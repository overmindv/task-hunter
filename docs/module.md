# Модуль парсинга задач

## 1. Назначение

Модуль парсинга задач — компонент образовательной платформы, отвечающий за сбор,
структурирование и хранение задач по программированию из внешних источников.

Задачи приводятся к единому формату, классифицируются по темам и сложности,
после чего становятся доступны пользователям для решения.

## 2. Типы задач

Модуль работает со следующими типами задач:

| Тип | Примеры |
|---|---|
| Алгоритмы | сортировка, поиск, графы, DP |
| Структуры данных | деревья, хеш-таблицы, стеки, очереди |
| Базы данных | SQL-запросы, нормализация, индексы |
| Бэкенд | REST API, авторизация, обработка ошибок |
| Поднятие инфраструктуры | Docker, CI/CD, деплой |
| Тестирование | unit, интеграционное, e2e |
| Ревью кода | поиск багов, code smells, рефакторинг |

## 3. Источники

Сбор осуществляется из следующих источников (разрешения на сбор получены):

### 3.1 Telegram-каналы

- **Поступашки "Аналитика"** — `@analytic_postupashki`
- **Поступашки "МЛ"** — `@postupashki_ml`
- **Алгоритмы — Собеседования, Олимпиады, ШАД** — `@algoses`

Источник: посты с задачами, прикреплённые файлы, комментарии.

### 3.2 Веб-сайты

- **LeetCode** — `https://leetcode.com` (задачи с тестов и собеседований)
- **Codeforces** — `https://codeforces.com` (олимпиадные задачи)
- **CodeRun** — `https://coderun.yandex.ru` (задачи от Яндекс)

Источник: HTML-страницы задач, API (если доступен), RSS-ленты.

## 4. Поток данных

```
Источник → Адаптер источника → Сырые данные → Пайплайн парсинга
  → Нормализация → Классификация → Хранилище
```

### 4.1 Сбор (Source Adapters)

Каждый источник представлен адаптером, который:

- Подключается к источнику (Telegram API, HTTP-запрос, WebSocket)
- Собирает новые/обновлённые записи
- Преобразует в единый формат сырых данных (`RawTask`)
- Передаёт в пайплайн обработки

### 4.2 Пайплайн парсинга (Pipeline)

Последовательность шагов обработки:

1. **Извлечение** — выделение текста задачи из сырых данных
2. **Парсинг** — извлечение структурированных полей (условие, примеры, ограничения)
3. **Нормализация** — приведение к единому формату, очистка от лишнего форматирования
4. **Классификация** — определение типа задачи и сложности
5. **Валидация** — проверка целостности и полноты данных

### 4.3 Хранение (Storage)

Нормализованные задачи записываются в базу данных.

## 5. Функциональные требования

1. **Сбор задач** — автоматический сбор новых задач из всех настроенных источников
2. **Дедупликация** — исключение дубликатов (по URL, тексту, хешу)
3. **Нормализация** — приведение к единому формату вне зависимости от источника
4. **Классификация** — автоматическое определение типа, темы и сложности задачи
5. **Обновление** — перепроверка источников на наличие новых задач по расписанию
6. **Ручной ввод** — возможность добавить задачу вручную через API
7. **Источник** — сохранение ссылки на оригинал задачи

## 6. Нефункциональные требования

1. **Устойчивость** — сбой одного источника не влияет на другие
2. **Идемпотентность** — повторный запуск не создаёт дубликатов
3. **Конфигурируемость** — источники включаются/отключаются через конфиг
4. **Расширяемость** — новый источник добавляется реализацией интерфейса
5. **Логирование** — каждый этап обработки логируется
6. **Метрики** — количество собранных задач, время обработки, ошибки по источникам

## 7. Языки и технологии

| Компонент | Язык | Причина |
|---|---|---|
| **Core: сбор, парсинг, нормализация, хранение** | Go | Производительность, типобезопасность, простая дистрибуция |
| **Классификация (rule-based)** | Go | Небольшая, легко встраивается |
| **Классификация (ML, будущее)** | Python | Экосистема NLP: transformers, scikit-learn, spaCy |

На старте весь модуль на Go. Python подключается только для ML-модели, если rule-based классификации станет недостаточно. В этом случае Python-сервис запускается как sidecar-процесс.
