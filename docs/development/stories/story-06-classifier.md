# Story 6: Classifier — классификация задач

**Для чего:** Реализовать rule-based классификатор для автоматического определения типа задачи, сложности и тегов — с архитектурным заделом под подключение ML-модели в будущем.

---

## Task 6.1: Реализовать rule-based классификатор типа задачи

**Для чего:** Реализовать классификатор, определяющий тип задачи (алгоритмы, БД, бэкенд, тестирование и т.д.) на основе правил и ключевых слов.

**Подробное описание:**

1. Создать директорию `internal/parser/classifier/`
2. Определить интерфейс `Classifier`:
   - `Classify(ctx context.Context, task *domain.Task) error`
3. Реализовать `RuleBasedClassifier`:
   - Для каждого `TaskType` составить набор правил:
     - **Алгоритмы:** ключевые слова: `массив`, `список`, `дерево`, `граф`, `сортировка`, `DP`, `динамическое программирование`, `бинарный поиск`, `BFS`, `DFS`, `O(n)`, `O(log n)`
     - **Структуры данных:** `стек`, `очередь`, `хеш-таблица`, `heap`, `куча`, `Trie`, `union-find`, `DSU`, `дерево отрезков`, `BIT`, `Fenwick`
     - **Базы данных:** `SQL`, `SELECT`, `JOIN`, `индекс`, `нормализация`, `транзакция`, `ACID`, `NoSQL`
     - **Бэкенд:** `API`, `REST`, `HTTP`, `middleware`, `аутентификация`, `авторизация`, `JWT`, `gRPC`, `сервер`, `эндпоинт`
     - **Инфраструктура:** `Docker`, ``, `CI/CD`, `деплой`, `контейнер`, `YAML`
     - **Тестирование:** `unit test`, `mock`, `stub`, `test coverage`, `TDD`, `интеграционное тестирование`
     - **Ревью кода:** `code review`, `рефакторинг`, `code smell`, `clean code`, `SOLID`
   - Правила проверяются по полям: Title, Description, Tags
   - Если несколько типов подходят — выбирается с наибольшим числом совпадений
   - Если ни один не подошёл — `TaskTypeAlgorithm` (по умолчанию для задач по программированию)
4. Метод `Classify` заполняет `task.Type` и `task.Tags`

**Тесты:**
- **Unit (golden):** задача про SQL → TaskTypeDatabase
- **Unit (golden):** задача про сортировку → TaskTypeAlgorithm
- **Unit (golden):** задача про Docker → TaskTypeInfrastructure
- **Unit (golden):** задача без ключевых слов → TaskTypeAlgorithm
- **Unit:** задача с ключевыми словами из двух типов — выбирается более подходящий
- **Unit:** пустое описание → TaskTypeAlgorithm, без паники

**Сторипоинты:** 3

## Task 6.2: Реализовать определение сложности задачи

**Для чего:** Реализовать логику определения сложности задачи (Easy/Medium/Hard) на основе анализа текста и дополнительных метаданных.

**Подробное описание:**

1. В `classifier/` создать `difficulty.go` или добавить метод в `RuleBasedClassifier`
2. Стратегия определения сложности:
   - **Если источник указал сложность** (LeetCode, Codeforces rating) — использовать её, сопоставив:
     - Easy → DifficultyEasy
     - Medium → DifficultyMedium
     - Hard → DifficultyHard
     - Codeforces: rating < 1200 → Easy, 1200-1600 → Medium, 1600+ → Hard
   - **Если источник не указал** — анализ текста:
     - Easy: короткое описание, нет сложных терминов (`прост`, `базов`, `лёгк`)
     - Hard: упоминание сложных алгоритмов (`LCA`, `heavy-light`, `Suffix Array`, `max flow`, `NP-полн`), длинное описание
     - Medium: всё остальное
3. Заполнять `task.Difficulty`

**Тесты:**
- **Unit (golden):** определение сложности по Codeforces rating
- **Unit (golden):** определение сложности по LeetCode labels (Easy/Medium/Hard)
- **Unit (golden):** определение по тексту (слова-маркеры лёгкой/сложной задачи)
- **Unit:** задача без маркеров → DifficultyMedium

**Сторипоинты:** 2

## Task 6.3: Добавить golden file тесты для классификатора

**Для чего:** Создать набор эталонных тестов (golden files) для классификатора, чтобы обеспечить регрессионное тестирование при добавлении новых правил.

**Подробное описание:**

1. Создать `classifier/testdata/` с директориями по типам:
   - `algorithms/`, `databases/`, `backend/`, `infrastructure/`, `testing/`, `codereview/`
2. В каждой директории — 2-3 файла с текстами задач (`.txt`) и соответствующий `.golden`-файл с ожидаемым результатом:
   - JSON с полями: `type`, `difficulty`, `tags`
3. Написать вспомогательную функцию `runClassifierTest(t *testing.T, inputPath, goldenPath string)`
4. Команда `-update` (через `flag` или `*testing.T`):
   - `go test ./internal/parser/classifier/... -update` перезаписывает golden-файлы
5. Тест проверяет, что классификатор возвращает те же результаты, что в golden-файле

**Тесты:**
- **Unit (golden):** каждый файл testdata → сверка с golden
- **Unit:** `-update` флаг корректно перезаписывает golden-файлы

**Сторипоинты:** 2
